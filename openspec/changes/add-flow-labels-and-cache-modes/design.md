## Context

Симулятор (`domain/simulate.ts`) уже различает, что шлёт каждый обработчик: сервер — запись в базы, чтение в кеши или базы, сообщения в очереди и шины; кеш — промахи в базы; очередь и шина — задачи и события. Но наружу выходит только сумма по связи (`SimResult.edges`), и доска подписывает связь числом. Снимки симулятора по урокам 1–13 ловят любое изменение чисел.

## Goals / Non-Goals

**Goals:**

- Ученик видит на каждой связи, что по ней течёт.
- Урок может показать оба паттерна кеша и сравнить их на одной доске.
- Уроки 1–13 считаются бит в бит как раньше.

**Non-Goals:**

- Write-through, write-behind и другие паттерны записи: запись по-прежнему идёт в базу через сервер.
- Режим отдельно для каждого кеша.
- Отказ read-through без запасного пути: упавший кеш сервер обходит в обоих режимах, как и раньше (иначе изменились бы уроки 4 и 10).
- Раскладка подписей без пересечений друг с другом: подпись только не ложится на блоки.

## Decisions

### D1. Вид потока — поле отправки, а не вывод по блокам

У каждой отправки (`Send`) появляется `kind: FlowKind`, его задаёт обработчик, который знает, что отправляет. `flowThrough` собирает по связи и сумму (`edges`, прежним кодом), и разбивку (`edgeKinds`). Альтернатива — выводить вид из видов блоков (сервер → кеш = чтение) — ломается на cache-aside, где сервер → кеш несёт и чтение, и заполнение, а сервер → база — и запись, и промахи.

| Отправитель | Получатель | Вид |
|---|---|---|
| Users, CDN, Rate limiter, Load balancer | дальше по пути | `requests` |
| Server | Database (запись), реплика при упавших базах | `writes` |
| Server | Cache, или Database и реплики без кеша | `reads` |
| Server (cache-aside) | Database и реплики | `misses` |
| Server (cache-aside) | Cache | `fills` |
| Server, Queue | Queue, Worker | `jobs` |
| Server, Event bus | Event bus, подписчики | `events` |
| Cache (read-through) | Database, реплика | `misses` |
| Worker | Database, Object storage | `writes` |

### D2. Подпись: самый полный текст, который помещается

Кандидаты от полного к короткому: «reads 192 · writes 48 rps», «reads 192 · writes 48», «reads 192 rps +1», «240 rps». Берётся первый, который короче связи на 16 px и в одной из точек связи (0.5, 0.4, 0.6, 0.32, 0.68) не ложится ни на один блок. Иначе подписи нет: так пропадают подписи вертикальных связей балансировщика, которые раньше наполовину прятались под блоками. Числа подписи — доли из симуляции, умноженные на плавный поток анимации, поэтому подпись меняется вместе с частицами. Подписи видны и в задаче, кроме моментов, когда ученик тянет блок или связь.

Названия видов: чтение, запись, задачи, события, запросы — родными словами (как в строке профиля трафика «запись 20%»), промах — английским `miss` (словарь инструментов курса: cache hit / miss), заполнение — родным словом.

### D3. Цвета видов

Приглушённые оттенки, отличимые от тревожных: запросы — прежний зелёный, чтение — синий, запись — фиолетовый, промахи — малиновый, заполнение — голубой, задачи — бирюзовый, события — оливковый. «Почти на пределе» (янтарный) и «потерян» (красный) по-прежнему важнее вида. Цвета живут в двух местах: `flowColors` (canvas частиц) и `--flow-*` в `styles.css` (точки подписи и легенды), светлые и тёмные.

### D4. Режим кеша — поле доски

`BoardDoc.cacheMode`, операция `SetCacheMode({ mode })`. Режим на доску, а не на блок: ученик ставит кеш сам, и операция над блоком, которого ещё нет, не применилась бы; урок переключает режим шагом. `reset()` возвращает `read-through`.

### D5. Cache-aside в симуляторе

Сервер с живыми кешами шлёт им всё чтение (`reads`). В cache-aside он ещё шлёт `reads × (1 − cacheHitShare)` поровну в свои живые базы и реплики (`misses`, пользовательские) и столько же поровну в кеши (`fills`, не пользовательские: потерянное заполнение не ошибка пользователя). Кеш в cache-aside ничего не шлёт и ничего не теряет, кроме сверх ёмкости. Задержка промаха: сервер + 2 мс кеша + база. Упавший кеш сервер обходит, как раньше: всё чтение идёт в базы.

### D6. Связь кеш → база в cache-aside

Новая связь отклоняется (`ConnectCacheAside`): отказ сразу объясняет паттерн. Связь, проведённая до смены режима, остаётся, но пустует (`isIdleCacheEdge`) и рисуется пунктиром с подсказкой; цель `NoLink({ from: 'cache', to: 'db' })` просит её убрать. После `setCacheMode('read-through')` без связи кеш → база промахи теряются, как раньше у кеша без хранилища.

## Risks / Trade-offs

- [Подписи длиннее и в плотной схеме перекрывают друг друга] → короткие варианты текста и сдвиг вдоль связи; полный разбор — в подсказке легенды.
- [Режим один на доску] → достаточно для урока 4; поле блока можно добавить позже, не меняя операцию.
