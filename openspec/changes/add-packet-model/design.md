## Context

Мотивация описана в proposal.md (раздел Why), требования — в `specs/packet-network/spec.md`. Здесь собраны решения о том, как модель устроена.

Исходные условия:

- В `apps/web/src/domain` уже есть образец чистой модели первого курса:
  - документ и операции `BoardOp` с отказами через `Result`;
  - симулятор `simulate`;
  - цели с кодами `DomainMessage` и фокусом.
- Модель пакетов — второй вид доски (`packet`, раздел 4.5 плана). Общий контракт `BoardKind` появится в `extract-board-kind`. Поэтому сейчас модель повторяет форму `domain/`, но живёт отдельно.
- Пока шла работа, общие файлы правили другие исполнители. Поэтому изменение — только новая папка `apps/web/src/net/` и эта папка OpenSpec.

## Goals / Non-Goals

**Goals:**

- Одна функция трассы, из которой следующие изменения получат анимацию, конверт, таблицы устройств, вывод терминала, ошибку браузера и ответы квизов.
- Каждая механика MVP объяснима одной фразой урока и закреплена тестом по сюжету урока.
- Всё, что может оказаться в Model плеера, описано через Schema.

**Non-Goals:**

- Механика волн В2 и В3: таблицы маршрутов, traceroute, видимый NAT и проброс портов, рекурсивный DNS и TTL записей, TLS-проверки, файрвол, VPN, Docker.
- Время и перегрузка, повторы TCP, MTU, VLAN, STP, IPv6 (таблица «Не моделируем» в 4.2).
- Тексты сообщений, доска, поверхности, квизы и DSL уроков.

## Decisions

### D1. Папка `net/` и граница зависимостей

| Модуль | Что в нём |
|---|---|
| `address.ts` | IP, маска, подсеть, частные адреса, MAC из id, разбор URL |
| `model.ts` | Schema документа и состояния |
| `message.ts` | коды `NetMessage` |
| `packet.ts` | намерение, слои конверта, хоп, изменения таблиц, итог, трасса |
| `wifi.ts` | правила радио и подключение |
| `doc.ts` | поиск, `NetOp`, `apply`, `foldNet`, `applyAll` |
| `topology.ts` | живые связи, сегменты, текущие адреса, пересечение каналов |
| `run.ts` | ход трассы и таблицы |
| `frames.ts` | кадры и мосты, ARP |
| `packets.ts` | IP, NAT, маршрут |
| `dhcp.ts` | готовность хоста и DHCP |
| `trace.ts` | DNS, намерения, `trace`, `traceAll`, `settle` |
| `goals.ts` | цели |
| `build.ts` | конструкторы устройств и операций с умолчаниями |
| `testing.ts` | домашняя сеть урока 1 и помощники для тестов |

Модель импортирует только `effect` и `defineTaggedUnion` из `foldkit/schema`. Это помощник Schema, тот же, что в `domain/`: он даёт конструкторы на union и исчерпывающий `match`, которых требуют соглашения проекта. Рантайм, вид и команды Foldkit модель не использует. Из `board`, `lesson` и `lessons` не импортирует ничего.

Рассмотренные альтернативы:

- **Положить модель в `domain/`.** Отклонено: другой вид доски, и в тот момент папку правили другие исполнители.
- **Взять `Schema.TaggedUnion` напрямую.** Отклонено: длинные конструкторы (`cases.X.make`) и расхождение с соглашениями.

### D2. Документ: устройства как union по роли

`Device` — union из пяти вариантов:

- `Host` с полем `kind`: pc, phone, laptop, server;
- `Switch`;
- `AccessPoint`;
- `Router`;
- `Internet`.

`kindOf` возвращает одну из восьми иконок плана. Плоская структура с необязательными полями отклонена: она допускает коммутатор с DHCP.

Правила документа:

- **Хост — один разъём.** Ноутбук либо в Wi-Fi, либо на кабеле. Урокам MVP второй интерфейс не нужен.
- **MAC** задаёт автор. Иначе он выводится из id хешем FNV-1a, первый байт `02` (локально администрируемый адрес). У роутера два MAC: LAN и WAN.
- **Id связи** — `a-b` в порядке операции. Поиск связи не зависит от порядка концов.
- **Связь роутера с облаком — его WAN.** Остальные связи роутера — LAN: встроенный коммутатор и точка доступа.
- **Петли L2 запрещены** при соединении. Проверка идёт по всем связям, кроме связей с облаком, через коммутаторы, точки и LAN роутеров. STP модель не моделирует.
- **Смена LAN** сдвигает пул и резервы на разницу сетей, как в домашних роутерах.

### D3. Радио: связь — это попытка, подключение вычисляется

Радиосвязь на доске значит «устройство рядом и пытается подключиться». Подключён ли телефон, решает функция от документа:

- Wi-Fi включён;
- SSID и пароль из сохранённой сети совпадают;
- есть общий диапазон;
- устройство в зоне.

Поэтому «неверный пароль» — это изменение сохранённой сети, а не связи. Ошибка видна сразу на всех поверхностях: на доске, в браузере и в целях.

| Константа | Значение |
|---|---|
| Зона 2.4 ГГц | 450 единиц доски |
| Зона 5 ГГц | 280 единиц доски |
| Пароль WPA2/WPA3 | не короче 8 символов |
| Каналы 2.4 ГГц | 1–13; пересекаются, если отличаются меньше чем на 5 |
| Каналы 5 ГГц | 36–165 из стандартного списка; пересекается только тот же |
| Режим «оба диапазона» | `channel` — канал 2.4 ГГц, 5 ГГц на канале 36 |

Цели `WifiSecurity` и `ChannelClear` в это изменение не входят. Для них есть функции пересечения каналов и проверки конфигурации Wi-Fi.

### D4. Состояние отдельно от документа

`NetState` хранит:

- таблицы MAC мостов;
- ARP-кэши;
- аренды DHCP;
- таблицу NAT;
- DNS-кэши;
- счётчики эфемерных портов (с 51514) и портов NAT (с 40001).

Состояние — свёртка трасс по порядку (`traceAll`). Это сохраняет принцип «доска = свёртка» из раздела 3.1 плана: операции `send` будут складывать трассы, а `play` — только показывать.

`settle(doc, state)` проводит DHCP для каждого хоста без аренды по порядку документа. Так выглядит сеть, где все устройства «включились». На таком состоянии проверяются цели, поэтому им не нужен журнал `send`.

### D5. Движок: кадр за кадром, пакет за пакетом

- **Уровень 2** (`frames.ts`). Кадр рассылается обходом в ширину по живым связям.
  - Каждая доставка — хоп.
  - Мост учит MAC отправителя. Broadcast и неизвестный адрес рассылаются во все порты, кроме входного; известный адрес — в один.
  - Получатель кадра на свой MAC или broadcast «принимает» его, остальные хосты выбрасывают.
  - Предел в 2000 доставок защищает от документа, собранного в обход `apply`.
- **ARP** запрашивается по требованию перед отправкой IP-кадра в LAN. Связь с облаком — точка-точка, без ARP.
- **Уровень 3** (`packets.ts`):
  - хост отправляет пакет в своей сети напрямую, иначе шлюзу, а подключённый прямо к облаку — облаку;
  - роутер уменьшает TTL, свою LAN отправляет в LAN, остальное — через NAT в облако; из WAN пропускает только ответы по таблице NAT;
  - облако уменьшает TTL, не возит частные адреса и доставляет тому, у кого этот публичный адрес на доске.
- **Ход трассы** (`run.ts`) — неизменяемая запись: хопы, состояние, счётчик пакетов.
  - Шаг трассы — `Result`: отказ сразу становится итогом и обрывает цепочку.
  - Заметку хопа можно уточнить после решения на третьем уровне, например «маршрутизирован», «не мой ARP» или причина отказа.
- **Время.** Задержки: кабель 1 мс, радио 3 мс, связь с облаком 20 мс. Хопы сортируются по времени прихода; сортировка устойчива и сохраняет причинность. Пакеты нумеруются по первому появлению на доске.

### D6. Что входит в трассу каждого намерения

| Намерение | Пакеты |
|---|---|
| `Browse(url)` | DHCP (если нет аренды), ARP (если нет в кэше), DNS (если имени нет в кэше), SYN, SYN-ACK, ACK, запрос, ответ 200 |
| `Ping(ip)` | DHCP и ARP при необходимости, эхо-запрос, эхо-ответ |
| `Resolve(name)` | DHCP и ARP при необходимости, DNS-вопрос и ответ; кэш не используется, как в `nslookup` |
| `DhcpJoin(device)` | Discover, Offer, Request, Ack; хост с ручным адресом отказывает |
| `Arp(ip)` | запрос и ответы всех владельцев адреса; кэш не используется, как в `arping` |

Для `https` между TCP и HTTP лежит слой TLS с SNI, без рукопожатия. Запрос уходит после прихода ACK к серверу, хотя на деле браузер шлёт его сразу. Так пакеты на доске идут по одному.

### D7. Итог: три варианта вместо четырёх

`Outcome` — это `Delivered`, `Dropped` или `Refused`.

- `TimedOut` из наброска плана сведён в `Dropped`: у отправителя любой молча погибший пакет — это таймаут. Место и код причины говорят больше.
- `Refused` — получатель ответил отказом: RST, «имя не найдено».
- Причина отказа пишется и в заметку хопа, где погиб пакет. `failingHop` находит этот хоп для фокуса цели и подсказки «погиб здесь».

Браузер (изменение 6) сопоставит итог с кодом ошибки по тегу причины:

| Причина | Ошибка браузера |
|---|---|
| нет связи, нет Wi-Fi | `ERR_INTERNET_DISCONNECTED` |
| RST | `ERR_CONNECTION_REFUSED` |
| «имя не найдено» | `ERR_NAME_NOT_RESOLVED` |
| остальное погибшее | `ERR_CONNECTION_TIMED_OUT` |

### D8. Цели

`GoalCheck` повторяет форму целей первого курса и добавляет то, что нужно сетевым задачам:

- `met`, `maybeFailure`;
- `focusDevices`, `focusLinks`;
- `maybeHop` и `maybeTrace` — по ним доска проиграет трассу и остановится на хопе гибели.

Правила проверки:

- **Состояние.** Цели по адресам и трассам проверяются на `settle(doc, state)`.
- **`NoAddressConflict`** группирует адреса по широковещательному сегменту: два дома могут оба жить в `192.168.1.0/24`. Публичные адреса (хосты в облаке и WAN роутеров со связью с облаком) должны быть уникальны все.
- **`CannotReach`** при провале фокусирует весь путь пакета: «вот как база видна снаружи».

### D9. Упрощения, которые знает урок

| Упрощение | Почему допустимо в MVP |
|---|---|
| Облако «Интернет» — один хоп третьего уровня, знает все публичные адреса доски | маршрутизация в интернете — урок 8 (В2) |
| Нет ICMP-ошибок: закрытый UDP-порт и истёкший TTL — молчаливая гибель с кодом | traceroute и ICMP Time Exceeded — В2 |
| TLS — слой с SNI без рукопожатия и проверок | сертификаты — урок 11 (В2) |
| Сервер всегда отвечает 200 на любой путь | урокам нужен факт доставки |
| Аренда DHCP без срока; отвечает первый сервер сегмента | сроки аренды курсу не нужны |
| У роутера нет своих служб: админки по HTTP, DNS-форвардера | админка — поверхность «панель», DNS роутер раздаёт через DHCP |
| Дальность Wi-Fi — расстояние на доске, без стен и мощности | «кольца дальности» плана |

### D10. Сообщения

Один union `NetMessage` с группами:

- отказы операций;
- причины неподключения к Wi-Fi;
- заметки хопов;
- причины итогов;
- цели.

Параметры — id, адреса, порты, протоколы. Готовых фраз модель не содержит. Где лежат тексты (`i18n/` рядом с `DomainMessage` или отдельный словарь курса), решит изменение, которое их добавит.

### D11. Тесты

- **Тесты-сценарии** — по сюжету каждого урока 1–7 (`scenarios.test.ts`). Каждый строит сеть урока, считает трассы и проверяет цели задачи: старт не решён, решение решает.
- **Механика и детерминизм** — `trace.test.ts`:
  - повторный расчёт;
  - Schema-валидность документа, состояния и трассы;
  - порядок хопов;
  - счётчики;
  - время пинга.
- **Операции, адреса и цели** — `doc.test.ts`, `address.test.ts`, `goals.test.ts`.
- **Адреса** в тестах только документационные (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`) и частные, домены — в зоне `.example`.

## Risks / Trade-offs

- [Сетевики увидят упрощения] → Таблица D9 и плашка «упрощено» в уроках. Каждое упрощение снимается механикой своей волны.
- [Трассы длинные: Browse с нуля — около 30 хопов] → У каждого хопа есть номер пакета, а внутренний слой показывает протокол. Доска фильтрует (`only: 'dns'`), а транспорт шагает по пакетам.
- [Цели считают трассы заново на каждой проверке] → Сети уроков малы (десятки хопов), расчёт — микросекунды. Кэш не нужен.
- [Состояние может устареть после правки документа: аренда у роутера, которого больше нет] → Аренда учитывается, только если роутер в сегменте хоста и адрес в его LAN. Иначе хост получает адрес заново.
- [Порядок ответов при конфликте адресов определяется порядком связей в документе] → Это детерминированно и закреплено тестом. Урок 6 рассказывает, что «побеждает последний ответ».

## Migration Plan

Миграции нет: модель — новые файлы, существующее поведение не меняется. Откат — удалить `apps/web/src/net/`.
