## Context

Мотивация — в proposal.md (Why), требования — в `specs/packet-network/spec.md`. Здесь решения о том, как расширение ложится на модель из архива `2026-10-30-add-packet-model` (её устройство описано в design.md архива, D1–D11).

Исходные условия:

- Модель чистая: документ `NetDoc`, состояние `NetState`, трасса `trace(doc, state, intent)`, цели `checkGoal`. Импортирует только `effect` и `defineTaggedUnion`.
- Параллельно другой исполнитель переделывает плеер и реестр (несколько курсов, квизы, контракт `BoardKind`). Поверхности и уроки строятся позже на этой модели. Поэтому изменение не трогает ничего вне `apps/web/src/net/`.
- Механика входит только вместе с уроком, который её использует (риск «эмулятор сети», план 4.7). Таблица «Не моделируем» плана остаётся в силе.

## Goals / Non-Goals

**Goals:**

- Каждый сюжет уроков 1–16 считается моделью и закреплён тестом-сценарием.
- Поверхности (терминал, браузер, настройки Wi-Fi, панель) — тонкие виды над чистыми функциями модели. Всё, что ученик делает, — операции одной свёртки, поэтому «Показать решение» и журнал работают без особых случаев.
- Детерминизм прежний: счётчики, константы, порядок документа.

**Non-Goals:**

- Доска, поверхности, квизы, DSL уроков, `BoardKind` — следующие изменения.
- Переключатель вывода терминала по ОС (`add-terminal-os-flavors`).
- Время и перегрузка, повторы TCP, MTU, VLAN, STP, OSPF, BGP, поведение IPv6, настоящая криптография, физика радио сверх правил.

## Decisions

### D1. Мир сети: одна свёртка для документа и состояния

`World = { doc, state }`. `NetOp` получает операции мира:

| Операция | Действие |
|---|---|
| `Send(intent)` | трасса намерения, состояние после неё остаётся |
| `Wait(seconds)` | логические часы `state.clock` идут вперёд |
| `RunCommand(device, line)` | действие команды терминала (её операции), запись в журнал команд |
| `IssueCertificate(device, names, ca)` | проверка ACME HTTP-01 трассами от CA; успех кладёт сертификат в документ, неудача — отказ операции |

`applyWorld` применяет любую операцию, `foldWorld` пропускает отказанные (как доска), `applyAllWorld` останавливается на первом отказе (контент и тесты). `apply(doc, op)` для операций мира возвращает документ без изменений: операции мира применяет только `applyWorld`.

Почему так, а не отдельный union для мира: план (3.1, 3.2) говорит об одном журнале операций задачи, куда попадают и `send`, и `run(device, command)`. Один union проще поверхностям и `BoardKind`.

Вывод команды не хранится: `commandTranscript(world, ops)` пересчитывает его свёрткой, поэтому «Показать решение» выводит то же самое.

### D2. Провайдеры: облако и транзитные роутеры

Новый вид устройства `Transit` — роутер провайдера: один адрес, MAC и необязательный CGNAT (публичный адрес). Облако «Интернет» и транзитные роутеры — **узлы провайдера**:

- их связи — точка-точка третьего уровня без ARP (как связь с облаком в MVP);
- маршрут — кратчайший путь по живым связям провайдеров до владельца адреса назначения; обход в ширину по порядку документа, поэтому детерминирован;
- частные адреса и `100.64.0.0/10` не возятся, кроме доставки `100.64/10` прямому абоненту транзита;
- каждый узел уменьшает TTL; транзит отвечает ICMP Time Exceeded со своего адреса, облако молчит (`* * *` в traceroute) — это чёрный ящик, который урок 4 раскрывает транзитными роутерами.

Альтернатива — «раскрыть» облако только на доске. Отклонено: хопы не совпали бы с анимацией и квизом `NextHop`.

### D3. Роутер: WAN, маршруты, NAT, проброс

- **WAN роутера** — связь с узлом провайдера или с роутером, в LAN которого лежит WAN-адрес (роутер за роутером). Во втором случае WAN — обычный Ethernet: ARP, шлюз — LAN-адрес верхнего роутера. Так получаются двойной NAT и вторая сеть офиса.
- **Таблица маршрутов**: подключённая LAN, статические маршруты `сеть/маска via адрес в LAN` (длиннейший префикс), сеть VPN-сервера, маршрут по умолчанию в WAN. `routeTable` отдаёт её строки карточке роутера.
- **NAT** можно выключить (`nat: false`, режим маршрутизации): тогда из WAN пропускается трафик в LAN, если пускает файрвол роутера.
- **Проброс порта** `proto/порт → адрес:порт`: входящий на WAN проверяется по таблице NAT (ответы), затем по пробросам. Проброс добавляет строку NAT вида `forward`, ответ сервера уходит по ней.
- **CGNAT** — у транзита: пакет из `100.64/10` наружу получает публичный адрес провайдера; входящий без строки выбрасывается. Проброс на домашнем роутере за CGNAT не помогает — это видно трассой.
- **ICMP**: истёкший TTL на роутере и транзите порождает Time Exceeded отправителю. В ошибке есть цитата исходного пакета, поэтому она проходит обратно через NAT. Пакет на закрытый UDP-порт по-прежнему гибнет молча.

### D4. traceroute

Намерение `Traceroute(host)` шлёт эхо-запросы с TTL 1, 2, 3… (как `traceroute -I`) по одному на TTL. Каждая проба — отдельный пакет трассы. Строка ответа: TTL, адрес и устройство ответившего или «молчание», время. Конец — ответ цели, предел в 12 хопов или три молчания подряд.

### D5. DNS: записи, TTL, рекурсия, кэши

- Запись: имя, тип (A, AAAA, CNAME, MX, TXT, NS), значение, TTL.
- Сервер с UDP 53 отвечает по своим записям: точное совпадение, CNAME с продолжением внутри своих записей, NS ниже по дереву — ответ-направление (referral).
- **Справочная** (`resolver: true`) знает, кто на доске отвечает за имя (самая длинная зона, затем порядок документа), и спрашивает его пакетами трассы; CNAME вне своей зоны раскручивается новым вопросом. Цепочку корень → зона → провайдер не строим: урок 10 рассказывает её словами. Ответы кэшируются до `clock + TTL`, «не найдено» — нет.
- **Общедоступные справочные** `1.1.1.1` и `8.8.8.8`: если их нет на доске, отвечает облако по записям доски. Роутер отвечает только по своим зонам (шлюз VPN — зона офиса); пересылки DNS у домашнего роутера нет, урок 3 называет это упрощением.
- Устройство тоже кэширует ответы (stub), с тем же сроком. Открытие страницы и ping берут из кэша, `nslookup`/`dig` спрашивают сервер.
- `Wait` проматывает часы: кэш истекает, и резолвер спрашивает заново. Так виден урок 10: «у друга старый адрес, пока не истечёт TTL».
- Сервер без роли справочной — прежний DNS-lite, сценарии MVP не меняются.
- Имена без сети: в контейнере — сервисы своего моста compose и `host.docker.internal`; у члена mesh — имена других членов.

### D6. TLS как таблица правил

Сертификат — имена, издатель и срок (секунды логических часов). HTTPS добавляет два пакета: ClientHello с SNI и ServerHello с сертификатом. Браузер проверяет по порядку: издатель доверенный (список публичных CA и CA на доске), имя совпадает (точно или `*.зона` на один уровень), срок не истёк. Первая неудача — код, по нему браузер выбирает `NET::ERR_CERT_*`. Нет сертификата — `ERR_SSL_PROTOCOL_ERROR`. Криптографии нет.

Перенаправление: у слушателя порта 80 флаг `redirectToHttps`; ответ 301 с `Location`, браузер идёт по нему (не больше трёх переходов).

ACME HTTP-01: CA открывает `http://<имя>/.well-known/acme-challenge/…` своей трассой; ответить должен тот сервер, который просит сертификат. Сертификат выдаётся на 90 дней от `clock`.

### D7. Файрвол

`Firewall = { enabled, defaultIn, defaultOut, rules }`, правило — направление, действие (allow, drop, reject), протокол, порт, источник (CIDR). Первое совпавшее правило решает, иначе — умолчание направления. Где стоит:

| Где | Что проверяет |
|---|---|
| ОС хоста (`ufw`) | входящие и исходящие пакеты, открывающие соединение |
| security group облачного сервера | входящие до ОС |
| роутер | транзит WAN → LAN (проброс, режим маршрутизации) и LAN → WAN |

Проверяются только пакеты, открывающие соединение: TCP SYN, эхо-запрос, DNS- и DHCP-запрос, UDP на слушаемый порт. Ответы проходят (как conntrack). Сработавшее правило (или умолчание) пишется в хоп. Drop — молчаливая гибель (у отправителя таймаут), reject — RST для TCP, ICMP unreachable для остального (быстрый отказ).

Публикация порта Docker обходит файрвол ОС, но не security group — как в жизни, и урок 16 этому учит.

### D8. VPN, туннель и mesh: конверт в конверте

Инкапсуляция — слой `Tunnel` в конверте, за ним внутренний IP-пакет: `[кадр, IP, UDP, Tunnel, IP, TCP, …]`.

- **VPN-клиент** на хосте: сервер, свой адрес в сети VPN, маршруты (full `0.0.0.0/0` или split), DNS. Маршруты VPN проверяются раньше подключённой сети (корпоративный клиент без доступа к локальной сети), кроме адреса самого сервера. Поэтому full tunnel «съедает» принтер.
- **VPN-сервер** на роутере: принимает UDP на своём порту, разворачивает пакет, запоминает конечную точку клиента в состоянии и маршрутизирует внутренний пакет как из LAN (NAT наружу). Ответ в сеть VPN заворачивается обратно к запомненной конечной точке. Рукопожатия и ключей нет.
- **Ретранслятор туннеля** — хост в облаке с доменом. Агент на ноутбуке открывает исходящее соединение (строка NAT дома) и регистрирует публичное имя. Запрос к имени ретранслятор отправляет вниз по этому соединению, агент отдаёт его локальному порту.
- **Mesh** — члены сети шлют «привет» по UDP 41641 координатору (строка NAT дома) и получают адрес `100.100.0.x` по порядку и имя. Пакет на адрес или имя другого члена идёт через координатор (как DERP); прямых соединений через NAT не строим.
- `settle` поднимает туннели и mesh так же, как DHCP: цели проверяются в «включённой» сети.

### D9. Docker

- Контейнер — хост вида `container` со ссылкой на хост Docker и имя сети (`bridge` или имя проекта compose). Связь с хостом — `virtual`, точка-точка.
- Мост хоста задаёт урок (`dockerHost(..., { bridge: '172.18.0.1/16', network })`); шлюз моста — сам хост. Имена сервисов работают, если сеть не `bridge`.
- `docker compose up` пересоздаёт контейнеры по файлу и сохраняет их адреса; новые получают следующий свободный адрес моста. Файл и запущенная конфигурация различаются до `up`.
- Здоровье: контейнер с зависимостью из переменной (`DATABASE_URL`) работает, только если достаёт до неё; иначе его порты отказывают, а `docker ps` и `logs` показывают перезапуск.
- `localhost` в контейнере — сам контейнер. Имена сервисов разрешаются только внутри сети compose, `host.docker.internal` — шлюз сети. Остальные имена — через DNS хоста.
- Публикация `-p [ip:]порт:порт_контейнера` на хосте: входящий на опубликованный порт (и `localhost:порт` на самом хосте) уходит в контейнер с DNAT; исходящее из контейнера маскируется адресом хоста.
- Compose-файл — часть документа хоста (сервисы, порты, зависимость). `docker compose up` создаёт контейнеры по нему.

### D10. Приложение с зависимостью

Две формы зависимости: веб-сервер с прокси (`webServer(..., { upstream: '127.0.0.1:3000' })`) отвечает 200, если достаёт до приложения, иначе 502 с причиной; контейнер с зависимостью из compose без неё «падает», и его порты отказывают. Проверка зависимости — расчёт без хопов на текущем состоянии: это состояние приложения, а не часть трассы. Цель `CanReach` считает 4xx/5xx недоставкой и называет причину.

### D11. Терминал

`runCommand(doc, state, device, line, available)` → строки вывода с метками (для урока 15: `dnsTimeout`, `gatewayUnreachable`, `timeout`, `refused`, `loopbackOnly`, `certProblem`…), необязательная подсказка-код, операции действия, трассы для анимации и признак «программа держит терминал» (`npm run dev` до Ctrl+C). `available` — открытые уроками команды и детали вывода (`ping.ttl`, `ip.mac`, `ip.route`).

- Вывод не переводится и упрощён в стиле Unix (план 3.2). Числа — из трасс: TTL, время, адреса.
- `ipconfig` — синоним `ip a` с тем же выводом.
- Действия — только операции: `npm run dev` → `Listen`, `ping` → `Send(Ping)`, `docker run` → устройства, связи, публикации, `ufw allow` → правило. Поэтому свёртка `RunCommand` повторяет действие.
- Незнакомая команда или закрытая уроком (`available`) → подсказка `UnknownCommand`/`CommandLocked` со списком доступных, без операций.

### D12. Браузер

`browse(doc, state, device, input)` нормализует адрес (без схемы — `http://`), считает трассу `Browse` и отдаёт страницу (адрес, статус, защищено ли, сертификат, адрес клиента глазами сервера) или ошибку браузера:

| Причина итога | Ошибка |
|---|---|
| нет связи, Wi-Fi, адреса | `ERR_INTERNET_DISCONNECTED` |
| имя не найдено, нет DNS, гибель вопроса DNS | `ERR_NAME_NOT_RESOLVED` |
| RST, reject | `ERR_CONNECTION_REFUSED` |
| нет шлюза, нет ответа ARP | `ERR_ADDRESS_UNREACHABLE` |
| сертификат | `NET::ERR_CERT_COMMON_NAME_INVALID`, `NET::ERR_CERT_DATE_INVALID`, `NET::ERR_CERT_AUTHORITY_INVALID` |
| нет сертификата | `ERR_SSL_PROTOCOL_ERROR` |
| остальное погибшее | `ERR_CONNECTION_TIMED_OUT` |

### D13. Wi-Fi для поверхностей

- `nearbyNetworks(doc, device)` — точки доступа в зоне 2.4 ГГц с уровнем сигнала 1–4, защитой и диапазоном; точки «не на доске» (`onBoard: false`) тоже видны, как сети кафе и соседа из урока 1.
- `checkJoin(doc, device, ssid, password)` — подключится ли: своя сеть (есть радиосвязь) с верным паролем; открытая чужая сеть, чужая сеть и неверный пароль — разные коды.
- **Стены** документа сокращают дальность: каждая пересечённая стена добавляет к расстоянию штраф (5 ГГц теряет больше). Это правило, а не физика радио.

### D14. Тексты

Модуль `net/text/`: тип `NetTexts` — по функции на каждый тег `NetMessage`, поэтому пропуск не компилируется; `renderNetMessage(locale, message, names)` подставляет подписи устройств вместо id. Тест рендерит каждый код на каждом языке из образцов параметров и проверяет, что текст не пустой и не содержит `undefined`. Слова для новичков: «конверт», «роутер», «адрес»; технические названия (`TTL`, `NAT`) — только в кодах уроков, где они тема.

### D15. Тесты

- `lessons-local.test.ts`, `lessons-internet.test.ts`, `lessons-dev.test.ts` — по `describe` на урок, сюжет из сценариев `docs/plans/networks-lessons/NN-*.md`: старт задачи не решён, эталон решает, ответ квиза вычисляется, типичные ошибки дают свой код.
- Старые сценарии переименованы в `mechanics.test.ts` с привязкой к новым урокам, механика сохранена.
- `world.test.ts`, `terminal.test.ts`, `browser.test.ts` — свёртка мира, терминал и браузер; `text/text.test.ts` — каждый код на каждом языке.

## Risks / Trade-offs

- [Модель растёт] → Каждая механика привязана к уроку и тесту-сценарию; упрощения перечислены ниже, плашка «упрощено» в уроках.
- [Трассы длиннее: HTTPS +2 пакета, рекурсия DNS +6] → Номер пакета и фильтр по протоколу на доске (как в MVP); рекурсия идёт только у резолвера с подсказкой корня.
- [Сетевики заметят: mesh всегда через ретранслятор, VPN без рукопожатия, traceroute одной пробой на TTL, full tunnel отрезает LAN] → Это поведение популярных клиентов в упрощённом виде; описано в уроках 8 и 13.
- [Свёртка `RunCommand` пересчитывает трассы] → Сети уроков малы, расчёт — миллисекунды.

| Упрощение | Почему допустимо |
|---|---|
| Облако молчит на traceroute | урок 4 и 8 раскрывают его транзитами |
| Одна проба на TTL, эхо-запросы | вывод читается так же |
| Нет ICMP port unreachable для UDP | UDP-таймаут тоже честный итог |
| Роутер за роутером — только прямой кабель в LAN верхнего | двойной NAT и вторая сеть офиса этого хватает |
| Docker-сеть точка-точка без ARP | bridge как коммутатор рассказан словами |
| Нет рукопожатия VPN, ключей | криптографию не моделируем |
| Mesh через ретранслятор | DERP-режим реален, прямой путь — оптимизация |

## Migration Plan

Внешних потребителей модели нет, кроме её тестов. Изменения сигнатур (`Intent.Ping.host`, записи DNS, кэш) обновлены в тестах. Откат — вернуть `apps/web/src/net/` к архиву.
