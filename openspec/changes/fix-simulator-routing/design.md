## Context

Симулятор (`domain/simulate.ts`) считает поток по рангам блоков. Аудит `.shots/audit-ambiguity.md` нашёл четыре правила, из-за которых доска показывает не то, что говорит текст. Каждое меняем самым маленьким честным способом и не трогаем числа уроков, которых правило не касается.

## Decisions

### D1. Одна повышенная реплика

Если у сервера есть база, но все его базы упали, запись идёт в **первую живую реплику в порядке доски** (`doc.nodes`), а не делится между всеми. Порядок доски одинаков для всех серверов, поэтому серверы с одними и теми же репликами повышают одну и ту же. Чтение по-прежнему делится между живыми репликами. Отказ повышенной реплики повышает следующую.

Отвергнуто: выбирать по id или по порядку связей (разные серверы могли бы выбрать разные реплики); общий для доски «primary» (сервер, не связанный с ним, терял бы все запросы — урокам это не нужно).

### D2. 429 — не ошибка

`errorRate = потерянные пользовательские запросы / нагрузка`; `rejectedRate = отклонённые / нагрузка`. Прибор «Отклонено» уже был; «Ошибки» теперь показывает только сбои. Цель `MaxRejectedRate` проверяет долю отказов (например, что платный тариф не получает 429). Запросы, которые ограничитель пропустил, а сервер потерял, остаются ошибками.

### D3. Чтение в своём регионе

`nearby(from, stores)`: если у читающего блока есть регион и среди хранилищ есть блоки этого региона, читаем только из них, иначе из всех. Применяется к чтению сервера, к промахам cache-aside и к хранилищам кеша read-through. Блоки без региона и уроки без регионов не меняются. Запись идёт как раньше — в primary, где бы она ни стояла.

### D4. Очередь — равные partitions, шина — копии, задачи и события раздельно

Правило выбрано одно и простое: сообщение очереди принадлежит ключу (заказ, получатель, пользователь), ключи поровну разложены по живым обработчикам, как partitions. Обработчик берёт свою часть, сколько успевает; остаток — рост очереди. Это заменяет прежнее «отдать свободному» (water-fill): для одинаковых обработчиков числа те же, а для разных доска больше не прячет медленного за быстрым. Для чата это и есть «событие идёт на тот gateway, где сидит получатель», если получатели поровну разложены по gateways.

Шина не меняется: каждый подписчик получает полную копию. Сервер кладёт `jobsPerRequest` задач в каждую очередь и `eventsPerRequest` событий в каждую шину: так поток заказов в очередь matcher и поток координат в шину задаются отдельно.

### D5. Фоновые задачи

Число задач на запрос уже задаёт урок через `jobsPerRequest`; новое правило не нужно. Урок 7 оставляет 1 задачу на запрос и прямо говорит, что на доске только сервис оформления заказов, поэтому его числа не меняются.

- **06 read-replicas, `failover`:** replica-1 (новая primary) 800 → 960 rps (64 %), replica-2 800 → 640 rps (только чтение); p95 177 → 183 мс. D1.
- **08 rate-limiting:** «Ошибки» после rate limiter 50 % / 67 % / 33 % → 0 % (`place-limiter`, `bots`, `backpressure`). Новые цели `lb-in-path` и `no-failures` (на старте задачи не выполнена: 40 % ошибок). D2.
- **11 multi-region:** database 400 → 300 rps, replica-1 100 → 200 rps (US-серверы читают только из неё: app3/app4 → db 75 → 25, → replica-1 50 → 100), p95 148,1 → 147,1 мс; подпись `cap` 100 → 200 rps. D3.
- **13 url-shortener:** эталон — четыре server (3,60 $), после отказа одного 267 rps на server вместо 400. Разбор хвалит эталон.
- **05, 07, 09:** только числа в новых текстовых строках. В 07 `backlog: -0 → 0` (равные partitions вместо water-fill, числа те же).

## Risks

- Lessons, где обработчики очереди разной мощности, получают рост очереди там, где раньше его не было. В уроках 1–13 таких нет.
